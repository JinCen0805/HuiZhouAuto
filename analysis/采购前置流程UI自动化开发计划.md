## 1. 目标与成功标准

### 1.1 业务目标

把"每次测试下游流程都要找人手工跑前置数据"变成**一条命令生成一条可测的采购前置数据**，
覆盖：采购申请 → 纪检分配 → 分包 → 市场调研与论证 → 采购需求/审计/审查 → 采购方式分配 → 采购执行申请，
最终产出状态为 **`采购中`（status=9）** 的采购项目，供招标/开标/评标等后续测试直接使用。

### 1.2 成功标准（可度量）

| 指标 | 目标值 |
|---|---|
| 全链一键运行成功率 | 连续 3 次 3/3 成功；失败可定位到阶段并给出截图/接口日志 |
| 单次运行耗时 | P0（到待调研）≤ 5 分钟；全链（到采购中）≤ 30 分钟 |
| 数据可用性 | 生成 1 个采购申请 + N 个子包 + 1 个调研项目 + 论证报告 + 采购需求书 + 审计记录 + 审查记录 + 执行申请，关键状态断言通过 |
| 可重复性 | 同一环境、同一配置下可重复生成（不依赖已有半成品数据） |
| 可维护性 | 页面/接口改动时，只需改对应 PageObject/ApiHelper，不改流程层 |
| 可恢复性 | 任意阶段失败后可从该阶段断点续跑（基于 runId/申请单号），不从头重跑 |
| 数据清洁 | 所有生成数据带统一前缀，可一键按 runId 清理 |

### 1.3 不在本期范围

- 招标/开标/评标/定标/合同等"采购执行之后"的流程；
- 政府采购平台（GOV）链路（本地 GOV 后端 502）；
- 预算外申请 BT8 八节点审批（当前组织数据不满足，需单独补数据，见 §12）；
- 自动撰写 OnlyOffice 正文（采购需求书/审计报告正文）、智能生成审批意见；
- 生产环境改造、性能/安全测试。

## 4. 总体方案（对评估结论的落地）

### 4.1 架构分层

```
flows/       阶段编排：S01…S20，阶段间做前置校验、后置断言、断点续跑
pages/       PageObject：每页一个模块，集中维护 URL/iframe/选择器/动作
api/         ApiHelper：纪检分配、professor mock 电话确认、扫码签名、
             立即发布、审批兜底办理、文件上传
core/        会话（多账号登录+缓存）、浏览器、配置、日志、断言、报告、重试
fixtures/    附件、模板、响应文件、评审指标、业务默认值
scripts/     env-check、run-demo、run-flow、cleanup
```

### 4.2 混合边界（哪些必须走接口）

| 环节 | 处理方式 | 原因 |
|---|---|---|
| 登录/选平台 | HTTP 登录（验证码万能码）+ cookie 注入 | 稳定、快、抗页面改版 |
| 纪检分配监督员 | 接口 `/jjjc/supervise/assign` | 跨系统、跨库写状态，UI 收益低 |
| 专家抽取+电话确认 | 手动抽选 + professor mock 回调 | 本地语音关闭，纯 UI 不可行 |
| 论证报告扫码签名 | `createReportSignatureQr` + `confirmReportSignature`（base64） | 需真人手机，接口可模拟 |
| 调研公告定时发布 | 立即发布 `pushOneById` | 时间不可控 |
| 审批待办（兜底） | `GET /workflow/task/list/todo` + `POST /workflow/task/complete` | UI 审批页可做，接口作为兜底/加速 |
| 主体业务操作 | UI | 保留"真实用户操作"的业务验证价值 |

### 4.3 可恢复编排（关键设计）

- 每个阶段函数输入：`runContext`（runId、账号、申请单号、阶段参数、已完成阶段记录）；
- 每阶段结束写 `state.json`（阶段、状态、关键 id、截图），失败时保留现场；
- 支持 `--from S11 --runId xxx` 断点续跑；
- 全链回归时用新 runId；调试时用旧 runId 续跑，避免重复造数。

### 4.4 开发期并行技巧

本地库现有多状态存量数据（待编制/待审计/待审查/待分配/待执行各有存量），
各阶段脚本可**分别对着存量数据开发调试**，不必等上游阶段跑通后再串行开发——
这是双人并行方案成立的基础。

## 10. 质量与验收

### 10.1 分层测试

| 层 | 内容 | 频率 |
|---|---|---|
| L1 冒烟 | 14+ 页面可加载、关键接口 200/业务码、菜单渲染 | 每次运行前 |
| L2 分阶段 | S01~S20 各自可独立运行（对着存量数据） | 开发期每日 |
| L3 全链 E2E | 一条命令从头到尾 | 每个里程碑 + 交付前 |
| L4 稳定性 | 连续 3 次 + 隔日 1 次；记录成功率/耗时/失败阶段 | M6 |

### 10.2 Definition of Done（每个任务）

- 代码：无硬编码密码/环境地址；选择器集中在 PageObject；失败自动截图+日志；
- 功能：正向主链通过；至少覆盖 1 个边界（如空列表/按钮置灰/接口失败提示）；
- 断言：以业务状态/接口数据为准，不以"页面 200"为准；
- 数据：使用 runId 前缀；可被清理脚本识别；
- 运行：连续 3 次通过（单人任务至少 2 次）；
- 文档：README/配置项/已知限制更新。

### 10.3 运行指标

| 指标 | 目标 |
|---|---|
| P0 运行耗时 | ≤5 分钟 |
| 全链运行耗时 | ≤30 分钟（含专家/公告 mock 的等待） |
| 失败定位时间 | ≤10 分钟（报告直接指出阶段+接口+截图） |
| 重试策略 | 网络/超时类自动重试 2 次；业务校验失败不自动重试 |

### 10.4 数据清理

- 统一前缀：`UI自动化-{runId}-`（申请名、子包名、附件名、调研项目名）；
- 清理方式：优先页面/接口删除（草稿、子包）；无删除入口的记录按前缀做受控 SQL 清理（需授权）；
- 清理验收：按 runId 检索关键表无残留；保留最近 1 次运行数据供排障。

| 审计跨前端（HP+纪检）联调复杂 | 中 | 高 | 提前在 W1 摸清接口/账号；必要时该阶段转 API 为主 | 登录/跳转/接口反复 401/500 |

| 单点账号被占用/并发冲突 | 低 | 低 | 一账号一会话；串行执行；错峰 | 登录被顶 |
| 稳定性不达标（UI 抖动） | 中 | 中 | 关键动作增加等待/重试；M2 设置决策门：若某阶段成功率<90%，该阶段改 API 为主 | 连续失败 |

**API 为主**（这些阶段 UI 的业务价值较低），UI 只保留关键人机交互页面，以保证整体交付。

## 13. 协作与变更管理

- **节奏**：每周一计划、每天进展/阻塞同步、每周五演示可运行成果（不是 PPT）；
- **分支**：`automation/` 独立仓库/目录；不改业务仓库；环境配置改动（`db/infra/local-stack`、`openresty/local-dev`）单独提交/评审；
- **评审**：每个里程碑一次代码抽查（选择器集中、无密码、断言合理）；
- **变更**：范围/工期变化走"影响分析 → 重排关键路径 → 更新计划版本"；页面/接口变更当天记录到 `CHANGELOG`；
- **复盘**：每期结束记录"踩过的坑"（弹窗层级、固定列 DOM、iframe、接口方法等），沉淀到 Runbook。
